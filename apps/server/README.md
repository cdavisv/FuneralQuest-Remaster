# @fq/server

The Funeral Quest game server: Fastify over HTTP and WebSocket, SQLite storage, a day scheduler, and an admin API that replaces the original Windows sysop dialogs. It hosts any number of towns, each a `TownState` from `@fq/core` held in memory by a single writer and saved to SQLite after every step.

It also carries the player-safety features the app stores require: block, report, a moderation page and API for the operator, mutes, a strict word list, account deletion and data export (see "Player safety and moderation").

Game actions are plain HTTP `POST`s that return the next `View`. The WebSocket carries only what other players or the clock cause: chat lines, broadcasts, "you have mail", a new day, a View the engine changed behind your back.

## Run it

```sh
pnpm install
pnpm --filter @fq/server dev                  # tsx watch, http://127.0.0.1:8080, ./data/fq.sqlite
FQ_ADMIN_TOKEN=$(openssl rand -hex 32) pnpm --filter @fq/server dev    # with the admin API on

pnpm --filter @fq/server typecheck
pnpm --filter @fq/server test
pnpm --filter @fq/server build && pnpm --filter @fq/server start       # bundle to dist/server.mjs and run it
pnpm exec biome check apps/server
```

With an empty database and no towns file the server creates two towns (see "Default towns" below): an Expanded flagship, `expanded`, and a Classic town, `main`. Configuration is environment variables only; `.env.example` lists and explains every one. The server does not read `.env` itself (use `node --env-file=.env`, your process manager, or Docker Compose).

### Docker

One image holds the game server and the web client, so one port gives a complete playable game:

```sh
cp apps/server/.env.example apps/server/.env     # set FQ_ADMIN_TOKEN (optional but wise)
docker compose up -d --build                      # from the repository root (or from apps/server)
curl localhost:8080/health                        # then open http://localhost:8080
```

`apps/server/Dockerfile` is built from the repository root (`Dockerfile.dockerignore` keeps `legacy/`, the animation frames of the art and every `node_modules` out of the build context). Its build stage installs the workspace, runs `pnpm --filter @fq/client build` (art derivation, type check, Vite, the PWA files) and bundles the server; the runtime stage holds only `server.mjs`, the server's npm dependencies and the built client, with `FQ_CLIENT_DIR=/app/client` already set. Game state lives in the named volume `fq-data` mounted at `/data`. A fresh volume starts with the two default towns (an Expanded flagship and a Classic one); `FQ_DEFAULT_TOWNS` in `.env` changes that. To create towns from a file, copy `towns.example.json` to `towns.json` and uncomment the two marked lines in `docker-compose.yml`.

The image does **not** contain the original sounds. To add museum mode (below), build with `FQ_INCLUDE_MUSEUM=1 docker compose build` (the build argument `INCLUDE_MUSEUM=1`), which copies the original client's files, Ruffle and the art manifest into `/museum`, and set `FQ_LEGACY_CLIENT=1` in `.env`.

## Sysop guide

- **Custom content packs.** Set `FQ_PACKS_DIR` to a directory with one subdirectory per pack, each in the format of `@fq/content`'s `loadPackFromDirectory` (`pack.yaml` with the pack `id` and optionally `extends: classic`, one YAML file per table, optional `overrides.yaml`; see `packages/content`). The server loads them all at start-up and refuses to start, naming the directory, file and entry, if one is invalid, if an id is one of the built-ins (`classic`, `vintage`, `expanded`), is used twice, or is longer than 32 characters. A town uses a pack by its `id`: `contentPack` in `FQ_TOWNS_FILE` or `POST /admin/towns`, or `PUT /admin/towns/:id/content-pack` to switch a running town. `GET /admin/server` lists what is available. Packs are read once; restart to pick up edits. A stored town whose pack has gone from the directory stops the start-up with a message saying so. Pictures are not checked against the art here (the server may not have it), so a pack's `picture` ids must exist in the client's art.

- **First start.** Set `FQ_ADMIN_TOKEN` (24+ characters; `openssl rand -hex 32`). Without it `/admin` answers 503. Keep the token out of version control and out of shared shells.
- **Towns.** Each town has an id, a name, a ruleset (`classic` or `expanded`), a content pack (`classic`, the original text; `expanded`; `vintage`, a deprecated alias of `classic`; or any pack from `FQ_PACKS_DIR`), a time zone and optionally a Blitz day length. Create them in `FQ_TOWNS_FILE` (created at start-up when missing; later edits to the file do not change an existing town) or with `POST /admin/towns`. After creation the database is the truth, and changes go through the admin API.
- **Rulesets.** `classic` is the 2001 game. `expanded` is the grown-up one (docs/expanded-rules.md): customers with traits, a parlor to upgrade, a graveyard, church Bingo, City Hall elections, the bank, parlor chains, the Reaper Club, played in 30-day seasons with the tournament reset. A town that names `ruleset: "expanded"` and no `contentPack` gets the `expanded` pack. Combinations the server refuses (422 `bad_town_config`, with the reason in `message`): an unknown ruleset or pack; a pack whose Expanded tables fail the engine's content check under the Expanded ruleset; `rules` (Expanded rule numbers) on a Classic town. Allowed: the `expanded` pack under the Classic ruleset (its Classic-format tables are compatible and the Expanded tables are unused), and any Classic-format pack (`classic`, `vintage`, a directory pack) under the Expanded ruleset, which then uses the Expanded starter tables for what the pack does not define. `GET /api/towns` carries each town's ruleset, a label and a short description for the lobby.
- **Default towns.** A fresh server (no towns in the database, no `FQ_TOWNS_FILE` entries) creates `expanded` ("Dead Calm", the Expanded flagship, a 30-day season that ends with the tournament reset) and then `main` ("Dead Calm Classic"). `main` keeps the id the single default town always had, so older scripts and clients keep working; museum mode, which only plays Classic, picks the first Classic town. To change that: `FQ_DEFAULT_TOWNS=classic` or `=expanded` makes just one of them; `FQ_CREATE_DEFAULT_TOWN=false` creates none (then create towns with `FQ_TOWNS_FILE` or `POST /admin/towns`); a towns file that creates at least one town replaces the defaults. The defaults are only ever created for an empty database: an existing server keeps the towns it has.
- **Expanded rule numbers.** The numbers in `packages/core/src/rules/expandedRules.ts` and `expandedTownRules.ts` are the same on every server, apart from a short list a sysop may change per town: the PvP and underdog numbers, the start of the town (church, City Hall, chains, hospital, Reaper Club, bank, graveyard, world) and a few others. `GET /admin/towns/:id/settings` of an Expanded town returns `expandedRules: { overrides, values, tunable }`: `tunable` lists every path (dotted, from the Expanded rules, for example `town.bank.loan.rate`) with the engine's current default and the range it accepts, `values` is what the town runs now, `overrides` is what this town changed. `PATCH` with `{ "expandedRules": { "town.bank.loan.rate": 0.05 } }` changes a number (use `null` to put the engine's number back); it applies to the next step, is saved with the town and audited. The negotiation's balance (`customer`, `psych`, `scoring`, `actions`, `hand`, `rating`, `upgrades`, `karma`) and the Daily Challenge loadout cannot be changed, nor can counts that size a table (bingo cards, shot glasses, market slots, chain places, the election's days). The list is derived from the engine at run time, so it follows the engine when the numbers or the rules change. The same `rules` object can be given when a town is created.
- **Seasons and the hall of fame.** When a town's tournament ends (the midnight after its last day, 30 days for Expanded by default), the engine resets the town. Just before, the server writes a hall-of-fame entry: the town, the season number, the end date, the winner and the final standings (top 100, with BP and, for Expanded, sales), and the chain standings (Expanded). It is public (`GET /api/hall-of-fame`), survives resets, rollbacks, restarts and deleting the town, and is never edited except by one thing: when an account is deleted, its name and parlor are replaced by "A Closed Parlor" in the entries that held them (the server remembers privately, in `hall_owners`, which account held which name, for entries made from now on). A season is not recorded when a sysop resets a town by hand (`POST /admin/towns/:id/reset`) because nobody won.
- **Game Settings.** `GET /admin/towns/:id/settings` returns every setting from the old Game Settings dialog (turns per day, starting money, odds, tournament length, max players, inactivity limits and so on) next to the defaults. `PATCH` changes any subset; the change applies at once and is saved and audited.
- **Days.** A normal town starts a new day at local midnight in its time zone. If the server was down, every missed midnight runs when it starts (the original ran only one). A Blitz town (`dayLengthMinutes`, for example 15) runs on a fixed clock counted from its creation. `POST /admin/towns/:id/new-day` forces an extra day without disturbing the schedule.
- **Players.** List and search players, edit any field the old player dialog had (money, BP, turns, tags, luck, script values and so on), kick, delete (a deleted parlor has its text taken out of the town, as an account deletion does; see below). Names must be free of the characters the original filtered (`?|=/\;:,{}@+`<>%$`), because a backtick in a name would be read as a colour code. Logon names cannot be changed.
- **Moderation.** The report queue, the page at `/admin/` and the actions on a report (warn, take down, rename, mute, kick, ban, dismiss) are described under "Player safety and moderation". Set `FQ_CONTACT_EMAIL` (shown on the public deletion page) and decide `FQ_BLOCKLIST_FILE`, the report limits and the retention periods in `.env.example` before opening the server to the public.
- **Bans.** Ban an account (also logs it out everywhere) or an address. Address rules are an exact address, a dotted prefix of whole octets (`203.0.113` means 203.0.113.0/24), or a CIDR block (`10.0.0.0/8`, `2001:db8::/32`). The original used a substring match, so banning `10.1.1` also banned `210.1.1.9` and `10.1.100.4`; this server cannot do that.
- **Rolling back.** The server takes a snapshot of each town at every new day, hourly when anything changed, before a reset or rollback, and at shutdown, and keeps the newest `FQ_SNAPSHOT_KEEP` (48). `GET /admin/towns/:id/snapshots` lists them; `POST .../rollback` restores one. Take a manual one first with `POST .../snapshots`. A restored town closes every connection; parlors that did not exist in the snapshot lose their account link.
- **Backups.** Everything is in one SQLite file (`FQ_DB_PATH`) plus its `-wal` and `-shm` files. Stop the server, or use `sqlite3 fq.sqlite ".backup copy.sqlite"`, and copy. Do not copy a live file with `cp`.
- **Logs.** JSON lines on stdout. Passwords, tokens and request bodies are never logged. The audit log (`GET /admin/audit`) records every accepted and rejected action, every engine effect and every admin change, and rows older than `FQ_AUDIT_RETENTION_DAYS` (90, `0` keeps all) are deleted by an hourly job. Only two things delete audit rows: that job, and an account's deletion (which removes the rows that hold what the account typed and keeps the moderation rows and a note that it happened). **Cafe talk is never written to the audit log or the server log**: the row for a chat action records only that a line was typed and how long it was.
- **The client's files.** When `FQ_CLIENT_DIR` is set the server serves the built client: files under `assets/` carry hashed names and are sent `public, max-age=31536000, immutable`; `index.html` and `sw.js` are `no-cache`; everything else is cached for an hour and revalidated by ETag. Scripts, styles, pages and vector art are sent brotli or gzip compressed to browsers that accept them (each file compressed once per ETag and kept in memory; API, admin and museum responses are never compressed). A reverse proxy that compresses too is harmless.
- **Behind a proxy.** Terminate TLS at a reverse proxy, forward `/` to the server (WebSocket upgrades on `/api/ws` too), and set `FQ_TRUST_PROXY` to the number of proxies so rate limits and bans use the real client address. Set `FQ_ALLOWED_ORIGINS` only if the web client is served from a different origin.
- **Shutting down.** `SIGTERM` or `SIGINT`: new work stops, sockets close with 1001, in-flight requests finish, each town's queue empties, a final snapshot is taken and the database is checkpointed. Every step was already committed when it happened, so a crash loses nothing but an in-flight request. Sessions survive a restart; players who do not come back are logged off after the idle time-out.

## Museum mode: the original 2001 client in the same town

`FQ_LEGACY_CLIENT=1` serves the unmodified Flash client of 2001 (`legacy/dist/public/flash/welcome.swf`), played with the [Ruffle](https://ruffle.rs) emulator, at **`/museum/`**. It plays the same town as the modern client: the Flash client's `request.xp` calls are translated into engine actions by `@fq/legacy-compat`, and every one runs inside the town's own queue and saves through the same commit as a modern action (one transaction with its audit rows, then pushes to modern players' sockets, presence and effects). It is **off by default**: with the flag off, `/museum` is a plain 404 and nothing from `legacy/` is served.

```sh
FQ_LEGACY_CLIENT=1 pnpm --filter @fq/server dev    # then open http://127.0.0.1:8080/museum/
```

- **Which town.** `FQ_LEGACY_TOWN` names it; empty means the first Classic town. A named town that does not exist stops the server at start-up with a message. **Classic only:** the original client knows nothing of the Expanded ruleset, so it never touches an Expanded town. If the named town is Expanded, or every town is, `/museum/` (and everything under it, including the client's `request.xp` calls) answers `409` with a short explanation page instead of breaking, and `GET /api/features` reports `museum: { enabled: true, available: false, reason }` so the web client's front door can hide the link. The moment a Classic town exists (or `FQ_LEGACY_TOWN` is pointed at one and the server restarted) it works again.
- **One account, either client.** The original client's log-on name and password are the server account's `login` and password (Argon2id, and the same lock after 10 wrong passwords in 15 minutes as the web log-in). The engine's player has `logon` equal to the account's `login`, and the parlor link is the same one the modern client uses (one parlor per account per town), so a player can use either client for the same parlor, and a modern player and a museum player see each other in the rankings, the cafe, rival visits, mail and everything else. Guest accounts have no password and cannot use the original client.
- **New User in the original client.** The server first checks what the original form cannot: the log-on name must be 3 to 20 letters, digits, dots, dashes or underscores, and the password 8 to 20 characters (the server's minimum of 8 and the original form's maximum of 20). Then it creates the account, or accepts an existing account that has no parlor in this town when the password matches; the engine then creates the player, which is linked to the account. Failures are shown in the original client's own error line. When sign-up is off (`FQ_SIGNUP_ENABLED=false`) new accounts cannot be made this way either. Logging on and New User share the web client's `FQ_RATE_AUTH_MAX` budget per address.
- **Cafe.** Lines from modern players reach the original client's players when it next polls; lines from the original client reach modern sockets as chat notices.
- **Days.** Midnight maintenance belongs to the server's scheduler, as always. A request from the original client first runs any day boundary that has passed.
- **Idle.** A museum player idle for the server's `FQ_IDLE_TIMEOUT_MINUTES` is logged off by the idle sweep like a modern one (the bridge's own 30 minute sweep never comes first).
- **Limits.** The original client shows what the 2001 game showed: no field-level messages from this server beyond those above, the 2001 name rules (the engine still strips the characters listed under "Names" below without saying so), and passwords up to 20 characters. A modern account with a longer password cannot log on with it in the original client.

**Where the files come from.** In a checkout, from `legacy/dist/public`, `assets/manifest.json` and `node_modules/@ruffle-rs/ruffle`. A bundled server (`pnpm --filter @fq/server build`, the Docker image) has no checkout around it, so `FQ_MUSEUM_DIR` names a directory holding `public/` (a copy of `legacy/dist/public`), `ruffle/` (a copy of the `@ruffle-rs/ruffle` package) and `manifest.json` (a copy of `assets/manifest.json`); the image's `INCLUDE_MUSEUM=1` build argument assembles exactly that at `/museum`. If the flag is on and a file is missing the server refuses to start and says which.

**Licence note about the sounds.** The original client's sounds and music are embedded in the SWF files under `legacy/`, and **they are licensed only for Funeral Quest and are not covered by the Proton SDK licence** that covers the source code and Akiko Robinson's artwork (see the repository README and `license.txt`). That is why they stay in `legacy/`, are never copied into the new tree or the default Docker image, and are served only when this flag is on, to a player who chose to open `/museum/`. The remastered game itself uses none of them. Ruffle is MIT or Apache-2.0 and is self-hosted (the page loads nothing from a CDN). This product includes software written by Seth A. Robinson (www.rtsoft.com).

`GET /api/features` tells a client whether it is on and playable (`museum.enabled`, `museum.available`, `museum.reason`) and that the Daily Challenge exists (`dailyChallenge.enabled`), so the web client's front door shows a link only when there is something behind it.

## HTTP API

All bodies are JSON. Every body is validated with a strict Zod schema (unknown keys are errors, strings and arrays are bounded) and must be under `FQ_BODY_LIMIT_BYTES` (16 KiB). Errors look like `{ "error": "code", "message": "text" }`, plus `view`, `field`, `richMessage` or `issues` where useful. `invalid_request` (400) carries `issues`: up to ten `{ path, message }` pairs (for example `{ "path": "parlor.name", "message": "Too small: expected string to have >=1 characters" }`) that never contain the value that was sent; the typed client keeps them on `ApiError.issues`. The player id is never taken from a request: it is derived from the session token and the town.

For the lobby: `rulesetLabel` ("Expanded"), `description` (what is different about playing it) and `season` (the season being played, from the hall of fame; null without a tournament) |

### Playing (rate limited per account, `FQ_RATE_ACTION_MAX` per window)

| Method and path                  | Body                                                           | Answer                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/towns/:townId/enter`  | `{}` or `{ parlor: { name, parlor, male, email? } }`           | 200 `{ view, created }`. First time needs `parlor`: 409 `parlor_required` without it, 422 `invalid_parlor` with the engine's message (`field`, `richMessage`) if refused, or, before the engine is asked, if a name contains a character it would silently strip (see below). Entering while already online ends the old session (`replaced`) |
| `POST /api/towns/:townId/action` | `{ action }` where `action` is an `Action` from `@fq/protocol` | 200 `{ view }`. 409 `rejected` with `view` if the engine refused it (unknown button, wrong overlay; nothing changed). 409 `not_in_game` if the session ended                                                                                                                                                                                  |

Requests for one town run strictly one after another, whoever sent them, in arrival order.

### WebSocket `GET /api/ws`

Open it, then send within five seconds `{"type":"hello","token":"fq_...","townId":"main"}`. The token travels in the message, never the URL. The player must already have entered the town. Replies and pushes are `ServerMessage`s (see below). The client may only send `{"type":"ping"}` (answered with `pong`); anything else closes the socket with 4400. Messages over 2 KiB are refused (1009), more than 12 in ten seconds closes the socket with 4429 (a client sends one ping every twenty seconds). A browser's `Origin` must be this server's own address or listed in `FQ_ALLOWED_ORIGINS` (4401 otherwise; connections with no `Origin`, such as the apps' native clients, are not checked). At most `FQ_WS_PER_ADDRESS` (100) sockets per network address and `FQ_WS_PER_PLAYER` (4) per parlor: past the first limit the new socket is closed with 4429, past the second the parlor's oldest socket is closed with 4000 to make room. Close codes: 4000 session ended (enter again), 4400 bad message, 4401 unauthorised, 4403 banned, 4404 no such town, 4409 not in the game, 4429 too many, 1001 server shutting down.

## Player safety and moderation

Both app stores (and good practice anywhere) require that a game with player-written text lets players report abusive content, block other players and delete their account, and lets the operator act on reports. This is all of it. The engine supplies `setBlocked`, `removePlayerText` and `renamePlayer` (packages/core `classic/blocking.ts`, `classic/moderation.ts`); the server owns accounts, reports, mutes, the word list, deletion and the screens.

### Blocks

- **Per account, in every town.** `POST /api/blocks` blocks the account that wrote what the player points at (a rankings row, a cafe line as displayed, a letter, an announcement, a name; see the target types below). The block lives in `account_blocks`, so it follows the account across towns, seasons, town resets, rollbacks and restarts. The engine's own lists are rebuilt from it (`TownRuntime.applyBlocks`): when a town loads, after a reset or rollback, when either player creates (or re-creates) a parlor, and **before every action or enter that steps the engine** if the block list changed since the town last matched it. A block recorded while another player's cafe line, letter or gift is already queued behind it is therefore applied before the engine computes that action.
- **The server screens its own pushes too.** Every cafe line the engine hands the host is dropped for recipients whose account blocks the account that caused it, even if the engine's list lags (the account's block is the truth). The same filter feeds museum players. The test holds the town's queue, files a block, lets the queued chat run, and then wipes the engine's list to show the second screen working alone.
- **What a block does:** the blocked player's letters, cafe lines (talk, `/me`, `/yell`, arrival and leaving lines) and gifts do not reach the blocker, they cannot be found by the blocker's `/give` and the blocker is left out of their pickers (Yang's deliveries, and in Expanded bank transfers and chain invitations), and battle quotes they write are not mailed to the blocker. **What it does not do:** it never shields from visits, fights, arson or theft; announcements and crime-page quotes in the shared newspaper stay in the paper for everyone (they are handled by takedown); it is one way (the blocked player still receives the blocker's lines); the blocked player is told nothing.
- Block list size is not capped; blocking yourself is refused. Deleting either account removes the block.

**Targets.** `POST /api/blocks` and `POST /api/reports` take `{ townId, target }`, where `target` is one of:

| `kind`                             | Fields                                | Resolved by                                                                                                                                                              |
| ---------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `player`                           | `playerId`                            | a rankings row or picker entry in that town                                                                                                                              |
| `name`                             | `name`                                | the active player with that display name                                                                                                                                 |
| `chat`                             | `text` (the line as displayed, plain) | the server's cafe window (below), only lines this player was sent                                                                                                        |
| `letter`                           | `text`, optional `fromPlayerId`       | the audit log's typed submissions, or `fromPlayerId` if the text is not found                                                                                            |
| `announcement`, `fortune`, `quote` | `text` (as displayed)                 | the audit log's typed submissions (`news:announcement`, `yangs:*-fortune`, `battle:quote`): the newest submission of that kind contained in the shown text is its author |
| `parlorName`                       | `playerId`                            | the parlor name of that player (reports only)                                                                                                                            |

### Reports

`POST /api/reports` `{ townId, target, category, note?, alsoBlock? }`. Categories: `harassment`, `hate`, `sexual`, `threats`, `spam`, `cheating`, `other`. The note is up to 500 characters. Answer `{ ok, duplicate, blockOffer: { name } | null, blocked }`: `blockOffer` says the author is known so the client can offer to block (or `alsoBlock: true` does both in one request); `duplicate` is true when the same player reported the same thing about the same account in the last 24 hours (nothing new is stored).

**What a report stores** (table `reports`): when it was filed; the reporter's account (moderators only; never in any answer a player can fetch; guests are flagged); the town; the kind, category and note; **the reported text itself**; **who wrote it** (account, login at the time, player id, display name and parlor name at the time); **where** (the cafe, mail, the newspaper, a fortune, a battle quote, the rankings); **when it was written** when the server knows; `verified` (the server matched the text to its own records: the cafe window or the audit log; an unverified report keeps the reporter's words, flagged, with no author to act on); and, for a cafe line, **the surrounding lines**: up to 10 lines before and 5 after, as that reporter saw them, copied from the window below, with the reported line marked. Status `open`, `dismissed` or `actioned`, who closed it, how, and why.

**How long.** An open report is kept until a moderator closes it. A closed one is deleted `FQ_REPORT_RETENTION_DAYS` (180) days after it was closed. Deleting an account removes the closed reports it filed or was the subject of; see "Account deletion".

**The cafe window.** The engine never stores chat, so the server keeps a small ring of recent cafe lines **in memory only**: at most `FQ_CHAT_BUFFER_LINES` (100) per town and `FQ_CHAT_BUFFER_MINUTES` (30) old, each with who caused it and who was sent it. A report copies the lines the reporter could see around the reported one; a line the reporter was not sent cannot be reported and never appears in their evidence. Nothing in it is written to disk unless a report captures it. A town reset or rollback empties the town's ring, and a deleted account's lines are removed from it.

**Rate limits.** Per account, `FQ_REPORT_MAX_PER_HOUR` (10) and `FQ_REPORT_MAX_PER_DAY` (30) reports (429 `report_limit`, with a plain message), plus the ordinary per-account action budget. A repeat does not count.

**Automatic safeguard.** When `FQ_AUTOMUTE_REPORTS` (3) **distinct registered accounts** (guests do not count, one account counts once) report the same account within `FQ_AUTOMUTE_WINDOW_MINUTES` (60), that account is muted from everything for `FQ_AUTOMUTE_HOURS` (24), pending review. The mute is marked automatic (`mod:automute` audit row). It tells the muted player nothing about who or how many. Dismissing the reports lifts an automatic mute once none is left open; a moderator can lift it at any time. `0` turns it off. The weakness is the usual one: a group of registered accounts can silence someone for a day, which is why it is a review queue item and not a punishment.

### Mutes

A mute stops one account publishing text of a kind, for a time. Scopes: `chat` (cafe talk, `/me`, `/yell`, `/give`), `mail` (letters and battle quotes), `announcements` (newspaper announcements and Expanded chain names) and `fortunes` (Yang's fortunes). **The server refuses the action before the engine sees it**, by the action's kind (`apps/server/src/moderation/service.ts`: `scopeOfAction`): `chat` actions, and `submitText` for the overlays `mailbox:compose` and `battle:quote` (mail), `news:announcement` and `cityHall:chainname` (announcements), `yangs:tiger-fortune` and `yangs:sparrow-fortune` (fortunes). The answer is `403 muted` with the message "You are muted from cafe talk and letters until Fri, 06 Nov 2026 14:00:00 GMT. This is a temporary measure by the moderators." and `mute: { scopes, until }`; cancelling a prompt (`text: null`), pressing buttons and everything else still work. `GET /api/me` lists the mutes in force (`mutes`). A mute expires by itself and can be lifted. Mutes apply to museum players too (below).

### The strict word list

A separate, stricter list than the engine's swear filter (which replaces words in some text): text that contains a listed word is **refused outright** in newspaper announcements, Expanded chain names, display names, parlor names, sign-up login names and moderator renames (`422 text_not_allowed`, or `422 invalid_parlor` with the field for a name; the message names no word). It is not shipped: `FQ_BLOCKLIST_FILE` names a file the sysop supplies, one entry per line (`#` comments):

```
word            a plain word, matched as a whole word
~word           matched anywhere, even inside other words or spread over spaces and symbols
sha256:<hex>    the same as a hash of the normalised word
~sha256:<hex>   a hashed "anywhere" entry
```

`pnpm --filter @fq/server blocklist:hash words.txt > blocklist.txt` turns a plain list into hashes so the plain list need not live on the server. Plain entries are hashed when the file is read and only hashes are kept in memory. Matching ignores case and accents, reads `0 1 3 4 5 7 @ $ !` as look-alike letters (and, because `!` ends sentences, reads symbols as separators on a second pass), and joins single letters ("f.l.u.r.b.o"). A refused text is **not** written to the audit log or the server log: the only record is an `safety:text-refused` row with what kind of text it was and the first eight hex digits of the entry's hash. A missing file stops the server at start-up with a message. This is not a moderation system: a hash list cannot catch what it does not list, and a determined player can misspell. It is the floor under reports, not a replacement for them.

### Account deletion, export and the public page

- **`POST /api/me/delete`** `{ password?, confirm: true }`: registered accounts must send their password again (wrong ones are throttled like log-ins and answer 401; a locked name answers 429); guests send only `confirm`. Answer 204 and the token is dead. A banned account cannot log in to do it; an operator deletes it (`DELETE /admin/accounts/:id`), after deciding what to keep.
- **What deletion removes.** The account, its sessions, its blocks (as blocker and as blocked), its mutes and its Daily Challenge runs. In every town, its parlor: the session ends; the engine's `removePlayerText` removes its queued letters, announcements, battle quotes and fortunes; `renamePlayer` and a sweep replace its names (current and earlier, from the audit log) in the stored paper, the Book of Deeds, other players' queued mail, other players' stored screens and the mayor's name by "A Closed Parlor"; the slot is deactivated, its record blanked (name, parlor, log-on, e-mail, mail) and its link removed; every rollback snapshot of the town that holds the player is cleaned the same way. The hall of fame entries that held its name show "A Closed Parlor". The closed reports it filed or was the subject of are deleted; the audit rows that hold what it typed are deleted; its lines leave the in-memory cafe window.
- **Delete the parlor or keep it as "A Closed Parlor"?** Deleted. The engine itself closes a parlor this way when it goes inactive: every rule already treats an inactive slot as gone (not ranked, not visitable, not a target, not in the tournament). A kept renamed parlor would stay on the board with the departed player's Bury Points, could be visited and robbed with nobody to answer, and would hold a rank no one could pass. The rename is for the history only, so old paper pages and other players' mail still read sensibly ("A Closed Parlor beat Bob") with nothing to trace back.
- **What it keeps, and why.** (1) A note in the audit log that a deletion happened (who asked, the counts; not the name). (2) The audit rows of moderation about the account (`admin:*`, `mod:*`): a ban, a mute, a dismissed report. (3) **Open reports about the account**, with their evidence (the reported text, names at the time, the cafe window), so abuse is not erased by leaving; they go when a moderator closes them and retention passes. (4) Open reports the account _filed_ keep their evidence but lose the reporter. Rollback snapshots are cleaned; **backups outside the server are not touched** (they age out with the operator's backup rotation), other players' audit rows that merely mention the name expire with `FQ_AUDIT_RETENTION_DAYS`, and what other players already read stays in their memory.
- **`GET /api/me/export`** returns everything stored about the account as JSON (`Content-Disposition: attachment`): `account`, `sessions` (times and **addresses**), `parlors` (the player record of each town, with a count of letters waiting but not their text), `blocks` (the display names of the players you blocked), `reportsFiled` (kind, category, your note, status), `reportsAboutYou` (**how many**, never by whom or what), `mutes`, `dailyChallenge`, `hallOfFame` (the names you hold in it), and `activity` (what you typed or did: your actions, sign-up, parlor creation, blocks and reports as events). It leaves out other players' text (letters to you), moderators' notes, reports' content, and audit rows about what the game did rather than what you typed.
- **`GET /account/delete`** is a public, script-free page that says how to delete an account from the game and how to ask without logging in, with a marked blank (`[CONTACT ADDRESS - OPERATOR TO FILL IN (set FQ_CONTACT_EMAIL)]`) until `FQ_CONTACT_EMAIL` is set. Use `https://<your host>/account/delete` as the deletion URL in the stores' forms. `GET /api/features` carries `safety: { reports, blocks, accountDeletion, contactEmail, deletionPath }` so the client can show the contact address.

### Museum mode

The original 2001 client cannot show a report or block button or a form, so a museum player can neither file reports nor block anyone from it (they can from the modern client with the same account: one account, either client). The server applies the rest to museum players anyway, at the one place it sees their requests (`museum/safety.ts`, which wraps the bridge's request handler): **blocks** reach them because they live in the engine's town state the bridge reads on every call (and the observer screen filters their cafe lines); **mutes** are checked on each request that would publish text (a cafe line, a letter, an announcement, a typed prompt), and the **strict word list** on names at New User and on announcements. The original client can only show what its protocol has: a muted cafe line is dropped and the player sees a notice in their own transcript; a muted letter or announcement, and a refused name or announcement, come back as the client's error line ("The server had a problem: ...") which also ends that log-on. Someone reported from the museum is found by their account like anyone else.

## Daily Challenge

One seeded day for everyone: a one-player Expanded town with a fixed loadout (20 turns, $5,000, a little stock, the tour done; `GET /api/daily` shows it), the same customers in the same order for every account, played once per account per day, ranked on a public board. It is `createDailyChallenge`, `startDailyChallenge`, `dailyChallengeResult` and `rankDailyChallenge` from `@fq/core` (docs/expanded-rules.md section 24) behind these endpoints.

- **The day** is the UTC calendar date (`"2026-11-06"`). Its seed is made from the date and a secret the server generates once and keeps in its database (`server_secrets`), so tomorrow's customers cannot be worked out in advance, and it is the same for every player and after a restart. (The engine's own seed from the date alone is what Solo's offline practice uses; it is not the online day.)
- **A run is a private town.** Each account's run is its own one-player `TownState` stored in `challenge_runs` and replaced after every action. Maintenance never runs on it, and nobody else can see or visit it. The action endpoint takes and returns exactly what a town's does (`{ action }` in, `{ view }` out), so the client's game screens play it unchanged; there is no socket (nothing can happen to the run behind the player's back).
- **Once per account per day.** `POST /api/daily/enter` starts today's run, or resumes the one in progress (the same screen, `created: false`). After the run is over it answers 409 `already_played` with the result. Guests (`POST /api/auth/guest`) can play; they get their result but never a place, and never appear on the board.
- **A run ends** when the turns are used up (the desk then shows the score and one Leave button), when the player quits (`desk:quit` with turns left), or when it sits idle for `FQ_IDLE_TIMEOUT_MINUTES` (15). The result is frozen at that moment. **An abandoned run counts as played**: it keeps what it earned (`abandoned: true`), it appears on the board if the account is registered, and it cannot be played again that day.
- **Ranking** is the engine's: BP earned in the run, then money gained, then fewer walkouts, then the name.

All of these need `Authorization: Bearer <token>` except the three public reads. Rate limits are the game actions' (`FQ_RATE_ACTION_MAX` per account).

Defined in `src/wire.ts`; the typed client imports the same types.

## How engine effects are dispatched

`src/game/effects.ts` is a single exhaustive `switch` over `Effect["kind"]`. It ends in `assertNever`, so when `@fq/core` adds an effect type, `pnpm --filter @fq/server typecheck` fails until the new case is written. Each case returns pushes, host commands, log lines and audit rows; `TownRuntime.commit` applies them after the town is saved. Separately, `diffPushes` compares the town before and after every step and pushes a changed View, or a `mail` notice for newly queued mail, to any other online player, which covers engine changes no effect announces.

| Engine effect        | What the host does                                                                                                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `log`                | structured log line; audit row                                                                                                                                                                                                                                           |
| `tv`                 | audit row only (the engine sends the cafe its own `chat` effect)                                                                                                                                                                                                         |
| `broadcast`          | `broadcast` notice to online players outside the cafe; audit row                                                                                                                                                                                                         |
| `chat`               | `chat` notice to exactly the players named in `to`                                                                                                                                                                                                                       |
| `playerCreated`      | audit row (the account link is made by the enter request that caused it)                                                                                                                                                                                                 |
| `playerDeleted`      | unlink the account's parlor (so it can start again), lobby View and `sessionEnded` to that player, close its sockets                                                                                                                                                     |
| `sessionEnded`       | stop reporting the player as connected, lobby View and `sessionEnded`, close its sockets                                                                                                                                                                                 |
| `tournamentReset`    | `tournamentReset` notice to every socket, unlink every parlor, close sockets; a snapshot of the old town was taken first                                                                                                                                                 |
| `tournamentResetDue` | reset the town (keeping settings, news and the Book of Deeds) after a snapshot. The engine no longer emits it (it resets itself and emits `tournamentReset`), but `@fq/core` still lists it as deprecated, so the exhaustive switch keeps the case. Remove both together |

**Presence.** The host reports connections to the engine with `setPresence`: connected when a player enters or acts, away when their last WebSocket closes while the session lingers, cleared when the session ends. After a restart every held session starts as away until its client acts or reconnects.

**Expanded.** The Expanded ruleset adds no effect kinds: its hits, Bingo, votes, loans, chain dues, duels and the rest are ordinary state changes made inside `step` and `runDailyMaintenance`, so they reach other players through the same `diffPushes` (a changed View, a `mail` notice) and the engine's `chat` effects. Midnight maintenance (`runDailyMaintenance`, run by the scheduler, the admin new-day and catch-up alike) resolves the Reaper Club's booked hits, draws Bingo, closes ordinance ballots and elections, adds bank interest and collects loans, and charges chain dues; `test/expanded.test.ts` checks each over HTTP through the scheduler with the fake clock. The server calls maintenance one day at a time so that a season's final standings can be recorded just before the reset (the result is the same as one call with `missedDays`). The engine's presence rules for duels and hits need nothing extra: they work on any active player, whether the host reports them connected or away, and the test covers both. If the engine adds an Expanded effect kind, the typecheck fails here until it is handled.

**Pending.** Nothing the engine currently emits is unhandled (checked against `Effect` and `sessionEnded`'s reasons `quit | timeout | replaced | reset`, all of which `EndReason` covers). `test/places.test.ts` walks the cafe, the visit screen, Yang's and the bank over HTTP with the real `classicPack`; if those modules add effects or presence rules, the typecheck says so.

## Accounts and sessions

Passwords are hashed with **Argon2id** through `@node-rs/argon2` (19 MiB, 2 passes, 1 lane by default; raise with `FQ_ARGON2_MEMORY_KIB` and `FQ_ARGON2_PASSES`). It is a native module, but it ships prebuilt binaries for Linux (glibc and musl), macOS and Windows as npm optional dependencies, so there is no compiler step, and it hashes on the libuv thread pool without blocking the event loop. `node:crypto` scrypt would have avoided the dependency but Argon2id is the stronger, recommended choice and the cost of the dependency here is small. The stored PHC string records its parameters, so they can be raised later. A login for an unknown name still runs a verification so timing does not reveal which names exist.

Session tokens are 256 random bits (`fq_` plus base64url), shown once, and stored only as a SHA-256 digest. They last 30 days (`FQ_SESSION_TTL_DAYS`), extended when used. Guest accounts have no password, so their token is the only way back in.

## Names

The engine silently removes some characters from a player's name and parlor name (`strip_dangerous_stuff`, `legacy/source/shared_util.cpp:126-156`): ``? | = / \ ; : , { } @ + ` < > % $`` and the ASCII codes 123 to 127, which adds `~` and DEL. A name such as `Bo@b` therefore became `Bob` and could collide with another player's `Bob` with a message that mentioned only `Bob`. The enter request now refuses these characters up front, before the engine is asked: `422 invalid_parlor`, `field` `name` or `parlor`, and a message that names the characters, such as `Names cannot contain @ and %.` or `Parlor names cannot contain , and /.` (`src/game/names.ts`; the characters are mirrored from `@fq/core`, which does not export them, and `test/names.test.ts` checks the mirror against the engine). Control characters were already refused (400 `invalid_request`).

## Persistence

SQLite through the built-in `node:sqlite` (Node 24 or newer), in WAL mode.

| Table                  | Holds                                                                                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accounts`, `sessions` | logins, Argon2id hashes, token digests                                                                                                                                             |
| `towns`                | one row per town: settings of the host (name, ruleset, pack, zone, day length, Expanded rule overrides), the schedule marker, a revision counter and the whole `TownState` as JSON |
| `parlors`              | which account owns which player slot in which town; checked against the player's log-on name on every use, so a reused slot can never hand one player another's parlor             |
| `town_snapshots`       | rollback points                                                                                                                                                                    |
| `audit_log`            | append-only (triggers refuse updates, and deletes outside the retention job)                                                                                                       |
| `ip_bans`              | address rules                                                                                                                                                                      |
| `hall_of_fame`         | one row per finished season (the town, the season number, the end date, winner, final standings and chain board as JSON); never edited or removed with the town                    |
| `challenge_runs`       | the Daily Challenge: one row per account per day (status, the frozen score, the run's `TownState` while it lasts)                                                                  |
| `account_blocks`       | who has blocked whom (account to account), with the name shown when it was made                                                                                                    |
| `reports`              | player reports with their evidence and how they were settled (see "Player safety and moderation")                                                                                  |
| `mutes`                | what an account may not publish, until when, by whom and why (including automatic ones)                                                                                            |
| `hall_owners`          | which account held which name in each hall-of-fame entry; never shown to anyone, used to take a deleted account's name out of the record                                           |
| `server_secrets`       | the Daily Challenge's seed secret, generated on first start. Keep it with the database: restoring an old copy restores old seeds, a new database means new customers               |

After each state-changing step the new state, its parlor changes and its audit rows are written in one transaction before the state becomes current in memory or anyone hears of it. A failed write leaves the old state in force and answers 500. At start-up all towns load and any missed days run before the server listens. Writing the whole town JSON each step is simple and fast for realistic towns: measured with `pnpm --filter @fq/server exec tsx scripts/scale.ts`, 800 parlors of which 5% are online come to about 0.6 MB of JSON and an action takes about 10 ms. It is not fast when everyone is online at once: every log-on is mailed to every parlor online, so the state grows with the square of the number online (tens of MB at 800) and an action takes 400 to 600 ms. If towns routinely hold hundreds of players online together, incremental persistence is the next step (see `docs/performance.md`).

## Rate limits

Per window (`FQ_RATE_WINDOW_SECONDS`, 60): `FQ_RATE_GLOBAL_MAX` per address for everything, `FQ_RATE_AUTH_MAX` per address on sign-up, log-in and guest, `FQ_RATE_ACTION_MAX` per account on enter, view and action (anything without a valid token counts against its address), and `FQ_RATE_ADMIN_MAX` per address on `/admin`, counting failed token guesses. The 429 answer is `{ "error": "rate_limited" }`. New accounts (sign-ups and guests together) are also capped per address per hour, `FQ_RATE_SIGNUPS_PER_HOUR` (0 means three times `FQ_RATE_AUTH_MAX`). An IPv6 address is counted as its subnet. At most `FQ_MAX_QUEUED_PER_TOWN` (256) operations may wait in one town's queue; past that, enter and action answer 503 `busy`. Password hashing runs four at a time with 64 waiting; past that sign-up and log-in answer 503 `busy` with `Retry-After`. Requests must arrive in full within `FQ_REQUEST_TIMEOUT_SECONDS` (30), headers within ten. Rejected actions are written to the audit log for the first 20 a minute per player; the rest are counted in one `action:rejected:suppressed` row. Rate limiting is per process and in memory.

## Typed client

`src/client/` is importable as `@fq/server/client`. `ApiClient` wraps the HTTP API (`signUp`, `logIn`, `guest`, `logOut`, `me`, `features`, `towns`, `town`, `enter`, `act`, `currentView`, `hallOfFame`, the Daily Challenge methods listed under "Daily Challenge", and `blocks`, `block`, `unblock`, `report`, `exportData` and `deleteAccount` for player safety). `ApiError` carries `status`, `code`, `message` and, when the server sent them, the player's `view` (a rejected action), the form `field` (a refused parlor form) and the `issues` of an `invalid_request`. `ServerTransport` implements the web client's `Transport` interface (`connect`, `send`, `onPush`, `close`) over it: `connect` enters the town and opens the socket, `send` posts an action, a rejected action throws an `ApiError` carrying the View, and the socket reconnects with exponential backoff and jitter, then fetches the current View and pushes it if it differs (pushes sent while disconnected are lost, and this repairs that). Cafe chat from others is turned into a pushed View (the last View with the line appended to `chat`); everything else is available from `onNotice`.

```ts
import { ApiClient, ServerTransport } from "@fq/server/client";
const api = new ApiClient({ baseUrl: "https://fq.example.com" });
await api.logIn("skelly", "…"); // or signUp, or guest
const transport = new ServerTransport({
  api,
  townId: "main",
  parlor: { name: "Skelly", parlor: "Skelly Rest", male: true },
});
// <App transport={transport} />
```

## Security notes

- Every body is a strict schema with length limits; player-typed strings reject control characters. Nothing builds HTML; text is `RichText` data from the engine.
- The acting player is always derived from the token. Strict schemas reject a body that names a player, and the engine checks every action against the View it last showed that player.
- The server never logs bodies or headers, and redacts `password`, `token` and authorization fields as a second guard. Error answers carry no internals.
- Responses carry `nosniff`, `no-referrer`, `DENY` framing and `no-store`. CORS allows only `FQ_ALLOWED_ORIGINS`. The web client's page is sent with a Content-Security-Policy (no inline script, no `eval`, own origin only; `FQ_CLIENT_CSP=false` turns it off); the admin page has a stricter one with a per-response nonce. `FQ_SECURE_COOKIES=true` marks museum mode's cookie Secure (set it behind HTTPS).
- The threat model, what was checked and the known limits are in [docs/security.md](../../docs/security.md).
- Not covered: TLS (use a proxy), CAPTCHA or e-mail verification on sign-up (the per-address limit is the only brake on account spam), and any filter beyond the engine's swear filter and the sysop's strict word list (a list cannot catch what it does not hold). Encryption of the SQLite file at rest is the host's disk.
