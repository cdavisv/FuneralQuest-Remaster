# @fq/client

The Funeral Quest web client. It draws any `View` from `@fq/protocol` and reports button presses as `Action`s through a transport. It contains no game rules: the server (or, for development, the mock transport) is the only author of what is on screen.

Vite, React 19 and TypeScript. Dependencies are `react`, `react-dom`, four font packages and the workspace's `@fq/protocol`, `@fq/server` (its typed browser client, `@fq/server/client`), `@fq/solo` (the Solo worker's client) and `@fq/core` (only for the `?expanded` development town, in a chunk nothing else loads); there is no state library, router or CSS framework. The chrome (cabinet, parchment, frame, plaques, map, newspaper, notepad, dialogs, front door) is drawn by an **art pack**: Classic, the original 2001 artwork exported as vectors, or Hand-drawn, the same chrome in CSS and inline SVG. Text, numbers, meters and button labels are always live HTML over the art.

## Run it

Play the real game, locally, in two commands (the first builds the client, starts `@fq/server` on a persistent database in `apps/client/.data/`, and serves both on one port):

```sh
pnpm install
pnpm --filter @fq/client play          # http://127.0.0.1:8080
```

Development, with hot reload (the Vite server forwards `/api`, WebSocket included, to a game server on `127.0.0.1:8080`, or to `FQ_SERVER_URL`):

```sh
pnpm --filter @fq/server dev           # the game server, ./data/fq.sqlite
pnpm --filter @fq/client dev           # http://localhost:5173 (add ?mock to use the scripted mock instead of a server)
```

Open an **Expanded town** in the browser (docs/expanded-rules.md), three ways:

- `http://localhost:5173/?expanded` (development, or any build: no server needed). The engine's Expanded ruleset runs on the page itself (`src/dev/ExpandedHost.ts`, a lazy chunk only this switch loads): you, and three quiet rival parlors who never act, starting at the paper. It is a showcase and a test bench, not the product's solo mode. Knobs in the address, all optional: `seed`, `money`, `karma`, `turns`, `luck`, `psych`, `tags=wood,silver,gold`, `bp`, `plots`, `day=N` (play N nights first, so the town has news, weather, ballots), `tour` (keep the guided first day; it is skipped otherwise), `events` (leave the random street events on; off by default so a walk is steady), `mail`, `rivals=0..5`, `start=<place id>` (begin inside a place). The desk gains an End the Day plaque. For example `/?expanded&money=90000&karma=20&day=12&start=graveyard`.
- A server with an Expanded town: a fresh `@fq/server` has two (the Expanded "Dead Calm" and the Classic one); the lobby names each town's ruleset. Solo: New career, Ruleset, Expanded (with Daily practice as a length).
- The Playwright suites do all three: `e2e/expanded.spec.ts` (the page's own town), `e2e/expanded-server.spec.ts` (the server) and `e2e/expanded-solo.spec.ts`.

Everything else:

```sh
pnpm --filter @fq/client art           # derive the Classic UI pieces (dev, build and test run this first)
pnpm --filter @fq/client test          # Vitest + Testing Library
pnpm --filter @fq/client typecheck
pnpm --filter @fq/client build         # output in apps/client/dist-build
pnpm --filter @fq/client e2e           # builds, starts a real server on a temporary database, drives it with Chromium, Firefox and WebKit
pnpm --filter @fq/client e2e:chromium  # one engine (also e2e:firefox, e2e:webkit); FQ_E2E_BROWSERS=chromium,firefox picks several
pnpm --filter @fq/client bundle:check  # the production bundle against bundle-budget.json (docs/performance.md)
pnpm --filter @fq/client perf          # the performance measurements (docs/performance.md)
pnpm --filter @fq/client capture       # re-capture the Expanded Views the tests draw (test/fixtures/expanded-views.json)
pnpm exec biome check apps/client
```

Which server the client talks to is decided in `src/net/config.ts`:

- `?mock` in the address (or a build with `VITE_MOCK=1`) uses the mock transport; in development `?fixture=negotiation1` (any key of `ALL_FIXTURES` in `src/mock/fixtures.ts`, for example `desk`, `map`, `news`, `cafe`, `stats`, `rankings`, `overlay.textInput`) starts it on that screen.
- Otherwise `VITE_SERVER_URL` (for example `https://fq.example.com`) names the server; unset means the page's own origin, which is what a build served by `@fq/server` wants. A different origin needs `FQ_ALLOWED_ORIGINS` on the server.

To see the three layouts, resize the window (the layout follows the viewport) or pick one under Settings, Layout. Phone is chosen below 640 px wide, in portrait, or when the window is under 480 px tall; wide at 1.55:1 and beyond; classic otherwise.

## Production build

`pnpm --filter @fq/client build` writes a static site to `dist-build/` that `@fq/server` serves when `FQ_CLIENT_DIR` points at it (`index.html`, hashed `assets/`, the web app manifest, icons, a service worker and an offline page):

- **Art.** The exported Classic art is about 65 MB, but nearly all of it is never fetched: the `<id>.frames/` animation folders (the client draws each picture from its single `<id>.svg`), the `ui/` sprite sheets (the pieces the client uses are derived at build time and bundled as hashed assets), and the contact sheets. The build copies only the single-frame pictures, 85 files, 4.5 MB, to `dist-build/classic/` (`tools/bundle-art.mjs`, unit-tested). Set `VITE_ASSET_BASE=https://cdn.example/classic` to host the art elsewhere instead (nothing is copied), or `FQ_BUNDLE_ASSETS=0` to leave it out. Missing art shows a labelled placeholder.
- **PWA.** `pwa/manifest.webmanifest` (standalone, 192 and 512 icons, a maskable one), `pwa/icons/*.png` (drawn from `pwa/icon.svg` by `pnpm --filter @fq/client icons`), `pwa/sw.js` and `pwa/offline.html` are emitted at the root. The service worker keeps the whole app at install (the page, every hashed file of the bundle including the Solo worker, the fonts and the Expanded places' pictures, listed by the build into `sw.js`: about 93 files; the 85 Classic pictures and the 13 Remastered redraws of Classic originals are kept best effort), answers a page load that cannot reach the network (or does not within 4 s) with the kept app, which then opens in Solo mode, and falls back to `offline.html` (which links to `/?solo`) only if nothing was kept. It never touches `/api`, `/admin`, `/health` or `/museum`. Installing needs HTTPS or localhost. The page does not register it inside the desktop and mobile apps (`window.fqWrapper`).
- **Which art is kept for offline play, and why.** The Expanded places and people (30 pictures, 0.74 MB) exist only in the Remastered pack, and an Expanded town shows them under every art selection (a Classic-art player needs them too), so they are part of the all-or-nothing install: an offline Expanded solo career shows its pictures. The 13 Remastered redraws of Classic originals (0.5 MB) are what only a player who chose the Remastered art ever sees, so they are best effort, like the Classic pictures. (`vite.config.ts` finds them from the bundle's `originalFileNames`.)
- **Sound.** The rendered audio is not in the install. The worker keeps each file as it is played, and once the game is usable (the page loaded, the browser idle, a few seconds later) the page asks it to fetch the rest in the background in the one format this browser plays (`src/audio/offlineFill.ts`; about 7 MB of Ogg Opus, 10 MB of AAC, two files at a time), so an offline Solo game is not silent and the first load stays as fast as before. Not on a data saver, not offline, not inside the native apps, not when `VITE_AUDIO_BASE` hosts the audio elsewhere. A new render (a changed `manifest.json`) starts the cache afresh.
- `pnpm --filter @fq/client play` (or `pnpm play` at the root) runs this bundle on the real server, which serves it itself (`FQ_CLIENT_DIR`); `--museum` also switches on the original 2001 client at `/museum/`, `--test` is what the end-to-end tests use.
- **Static file hosts.** Solo mode needs no server, so the same `dist-build/` works from any file host that serves it at the site root (the page, the service worker and the manifest use absolute paths: a sub-directory deployment is not supported). Without a server behind it the front door says the server cannot be reached and offers Solo.

## The front door

`src/net/` talks to the server; `src/shell/` is everything before a session. `Shell` is the client's top level when it plays against a server: it loads the public lobby listing (`GET /api/towns`), finds out who this device is (`GET /api/me`), and shows the title screen, the log-on plaque, the new-user screens and the static pages; once a town is entered it hands over to `Game`.

- **Online or solo** (first, when the build offers Solo, which it always does): two plaques, "Play online" (with the server's own state under it: "The server could not be reached.", "You are offline.") and "Play solo". The one that can work has the focus. When the server's `GET /api/features` says museum mode is on, a link to `/museum/` (the original 2001 client) is shown here and in the online door's links; it is absent otherwise and for servers that do not have the endpoint. A device that is offline (or `?solo` in the address, or a reload in the middle of a solo career) goes straight to Solo. A link "Online or solo" in the door's links comes back to this choice.
- **Title screen**: the original's gold logo over the dim graveyard (`logon-screen`), "Connecting to server..." that turns into the server's real status (the engine's game line, the next day's countdown, tournament days left, undertakers online), the server news, links to introduction, gameplay tips, rules, rankings and credits, and a town chooser when the server has more than one town. If the server cannot be reached it says so and offers Try again. If the engine says new accounts are refused (town full, tournament over) the reason is shown.
- **Log on**: the wooden plaque (`login-plaque`) with name and password, LOG ON, "or click" NEW USER, and Play as guest. A wrong password is shown under the password field, with the field emptied and focused again; nothing but the server's answer decides what is wrong.
- **New user**: the elderly clerk (`new-user-clerk`) in his frame. First form: log-on name and password (the server's rules are checked before the round trip: 3 to 20 letters, digits, dots, dashes and underscores; 8 to 128 characters). Second form: "What's your name?", "What is your parlor called?" and "What's your sex?" with the two skull icons (`skull-male`, `skull-female`, a radio group). Names with any of the characters the engine strips (`? | = / \ ; : , { } @ + ` < > % $ ~`, the same set the server now refuses with a message that names them) are refused up front, because the engine would otherwise strip them silently and report a confusing "already in use". The server's own complaint (a name already taken, `invalid_parlor`with its`field`) is shown under that field. The parlor is created by the first `enter` of a town; a returning account without a parlor in the chosen town lands on the same form. Guests (`/api/auth/guest`) go through the second form too.
- **Welcome back**: with a valid token the plaque says "Welcome back, <name>" with Open the parlor and Log out. A refused token is forgotten. A fresh tab never takes over a running session by itself; a reload mid-game goes straight back in (see below).
- **Exit** sends `exit`, then returns here. Log out revokes the token on the server and forgets it here.
- **Static pages** (`#/intro`, `#/gameplay`, `#/rules`, `#/credits`, `#/rankings`): the original's pages (`legacy/dist/public/pages/*.htm`) as data in `src/shell/pages.ts`, restyled on parchment over the graveyard, the Flash and browser notes dropped. Credits are built from the repository's `CREDITS.md` (`?raw` import, so editing that file updates the page): the original authors come first, then the remaster, then the original's special thanks. Rankings is the top ten of every town from the lobby listing. Settings has a Help section linking them in a new tab.

### What is stored, and why

**Only the session token** the server issued, in `localStorage` under `fq.token.v1`. Passwords are typed into the log-on and sign-up forms, sent once to `/api/auth/login` or `/api/auth/signup`, and never kept: not in storage, not in React state after the request, not logged (a test checks the page and storage after a log-on). Why `localStorage`:

- The token lasts 30 days and the game is played in short visits, often as an installed PWA that is closed and reopened. `sessionStorage` would log the player out every time; a cookie would need the server to set one (it does not), and a cookie that the browser sends by itself would bring CSRF back for an API that is otherwise immune to it, because every request here carries the token explicitly in `Authorization`.
- The cost is that script running on the page could read it. The client never builds HTML from game text (`RichText` renders spans; links only for http and https; no `dangerouslySetInnerHTML`), loads no third-party scripts, and the token is revocable (Log out) and expires. A guest account has no password, so for a guest this token is the only way back in; the plaque says so.
- Two non-secret conveniences: the last town (`fq.town.v1`, `localStorage`) and "this tab was playing" (`fq.playing.v1`, `sessionStorage`, so a reload resumes the game while a newly opened tab does not take over a session). Logging out clears the token and the flag. If storage is blocked the game works, without memory.

## Transport

`src/transport/types.ts` is the whole server contract the UI knows about:

```ts
interface Transport {
  connect(): Promise<View>; // open the session, resolve with the first View
  send(action: Action): Promise<View>; // report one action, resolve with the View that answers it
  onPush(listener: (view: View) => void): Unsubscribe; // Views nobody asked for: chat, rival attacks, a new day
  close(): void; // leave; no listener calls afterwards
}
interface LiveTransport extends Transport {
  onNotice?(listener: (notice: Notice) => void): Unsubscribe; // broadcasts, mail, a new day, session ended
  onConnection?(listener: (state: "online" | "reconnecting") => void): Unsubscribe;
}
```

`src/net/SessionTransport.ts` is the real one: `ServerTransport` from `@fq/server/client` plus what the UI needs on top (it does not duplicate any of its HTTP or socket logic):

- `connect` is idempotent while connected, so the front door can enter the town (and show the server's complaints on its own form) before the game mounts and "connects"; `close` takes effect a tick later and `connect` cancels it, which makes React's development double mount harmless.
- The push socket's health is visible through `src/net/observedSocket.ts`, which wraps the WebSocket constructor: it reports the server accepting the hello and the socket dropping, and sends the protocol's `ping` every 20 s so a connection that silently died (a laptop lid, a proxy that forgets idle sockets) is noticed after 50 s of silence and closed, which makes `ServerTransport` reopen it with backoff and resync the View. The UI shows a slim "Connection lost. Trying to get back in touch..." banner while that happens, never blocks play (actions go over HTTP), and says "Back in touch with the server." when it is over.
- A refused action (`409 rejected`, usually a click on a screen the player had already left) is not an error: the server's current View comes back and is simply shown. A lost connection, a rate limit and a server error become a `SendError` with a message of their own; a session that is gone (`not_in_game`, a 401) becomes the "session ended" screen.

`src/mock/MockTransport.ts` is the scripted stand-in (`?mock`): it walks fixture Views and enforces the same rule the real server does, that an action must match a button or overlay the last View offered. It handles `dismiss` and `exit` and its stats and rankings fixtures carry the structured `stats` and `rankings`.

## Protocol features

- `exit`: the round Exit button asks first, then sends `exit` (and leaves even if the server cannot be reached).
- `dismiss`: a message overlay is closed by sending `dismiss` with its `id`; the server answers with the next screen. Queued mail is therefore a sequence of overlays, one at a time, ending with the letter's `confirm` overlay ("Reply to this letter?" Yes/No). The dismissed message stays hidden while the answer is in flight, even if a push repeats it.
- Cancelling a prompt (Escape or Cancel on the notepad) sends `submitText` with `text: null`; Escape on a confirm answers no; on a picker, `playerId: null`.
- `textInput.initial` prefills the notepad (a quoted letter when replying), caret at the end.
- `View.stats` is drawn as a sheet on the status cabinet's parchment: Standing, Inventory (with the casket tag icons) and "You and your errands" columns, and the rating sentence on a line of its own. Unknown stat ids land in an "Other" column, so a new stat needs no client change; without `stats` the text is shown as before.
- `View.rankings` is a real table on the rankings cabinet: place, undertaker and parlor (with the rating title), Bury Points, status chip, a row marker for who is online. Without rows the text is shown.
- `CustomerPanel.moodLevel` drives the mood face: calm below 3, uneasy to 5, annoyed to 8, angry from 8 (the original's mood bands); without it the face falls back to the word.

Use it?") and only then fills the field; the choice is what `POST /api/daily/enter` gets as `parlor` (so the server never falls back to the login), is remembered on this device for the next day (never the log-on name unless the player chose it), and a guest is told they are not on the board (nothing is remembered for them). Resuming a run in progress asks for nothing. **Past days:** the results screen has a Day picker from `GET /api/daily/days` (newest first, today first) and loads each board with the leaderboard's `day` parameter. When the turns run out the desk shows the score with one Leave button; leaving, or Exit, goes to the results. `already_played` goes straight to the results.

### Art across packs, and what is still a stand-in

The original game has no art for the Expanded places. They are drawn in the Remastered pack (`assets/remastered/`, see `docs/art/remastered-notes.md`), and the client does not lock art to the pack that draws it:

- **Pictures.** A picture layer is tried from the selected pack, then from the Classic art, then from any other pack that draws the id (`pictureSources`, `src/art/packs.ts`). A player on Classic or Hand-drawn art still sees the graveyard, City Hall, the club and the new people; a player on Remastered still sees every original it did not redraw. The Classic art is not even asked for an id that only another pack draws (`virtual:fq-classic-ids`, made by `vite.config.ts` from `assets/classic`), so there is no request that can only fail.
- **Icons and pieces.** A pack that lacks an icon (the ledger, the town strip, the five parlor stages, the five monuments, the karma balance) or whose piece is only a stand-in (City Hall and the Reaper Club on the map, the parlor button) takes the real one from another pack (`shareAcross`). A pack's own art always wins, and the chrome (cabinets, geometry) is never borrowed.

## Solo mode

Offline play against computer rivals, with no server. `src/solo/` is the client's part; the game itself is `@fq/solo` (see its README), which runs the whole town, rivals included, in a module Web Worker.

- **Flow** (`SoloShell`): the list of saved careers (`SoloMenu`), the new-career form (`SoloSetup`), then the game. The form is in the new-user screens' style: your name, your parlor, the two skulls, then chips for how many rivals (0 to 7), how good (Easy, Normal, Hard), and a 30-day career or endless (there is no choice of wording: the text is the original in every mode; `vintage` stays a known pack id only so old saves load). The name rules are the online ones (a name the engine would strip characters from is refused up front); anything else the engine refuses (a name already used by a rival, say) is shown under the field. Rivals are picked by seed from the six personalities.
- **Saves.** One slot per career in IndexedDB (`funeral-quest-solo`, through `IndexedDbSaveStorage`), written a moment after anything changes (at most 0.8 s later; `Autosaver` in `SoloSession.ts`), at once when a day ends, when the tab is hidden (`visibilitychange`) and when the page is hidden or closed (`pagehide`), and when leaving to the list. A failed write (storage blocked or full) shows a banner that says so, with Export as the way to keep a copy. Each row has Continue, Export (downloads `funeral-quest-<name>-day-<n>.fqsave.json`) and Delete (asks first). Import reads such a file into a new slot (checked by the same migration code the worker uses; a file that is not a save, or a text pack this build lacks, is refused with the reason).
- **Reload.** `sessionStorage` (`fq.solo.playing.v1`) remembers the slot being played, so a reload goes straight back into the career, the same way the online door resumes. A new tab starts at the front door.
- **In the game.** `SoloSession` is a `LiveTransport` over `SoloWorkerClient`: the host's notices (new day, TV reports, mail) arrive on the same channel as the server's and use the same notice layer. The host adds an **End the Day** plaque to the desk, and between days the lobby View (Open the Parlor, Sleep Until Tomorrow) is drawn by `LobbyScene` like any other. While a night takes longer than 350 ms the page says so (`busyNote`); the page's own thread is not used for it (the e2e test measures the longest pause of the page's thread over two nights with seven rivals).
- **The worker** is `src/solo/soloWorker.ts` (`import "@fq/solo/worker"`, started by `platform.ts`), bundled by Vite as its own 400 kB chunk with the two built-in content packs; the page's own bundle imports only `@fq/solo/client` (the proxy, save files and storage), so the rules engine and the bots stay out of it. Tests give the shell a `SoloPlatform` with in-memory storage and an in-thread `serveSolo` (`test/solo.test.tsx`).

## The desk's choices

The desk has seven choices (the engine's Exit among them) and Solo adds an eighth. Plaques are for what depends on the moment: **Wait for Customer**, **Exit**, **End the Day**. The fixed places (map, paper, stats, rankings, letter) are the original's capsule menu, round brass icon buttons (`capsule-button-*` in the Classic art, derived as `capsule-*` pieces) with their names live under them, in `DeskMenu`. One row in the classic and wide cabinets (the plaques at the ends, the icons between, inside the text well); on a phone the icons are a row of five above full-width plaques. They are still buttons named by their label, the number keys still follow the View's order, and a pack without the icons (Hand-drawn) falls back to plaques. Any other screen draws its buttons as plaques as before.

## Notices

The push channel's non-View messages (`onNotice`) are folded by `src/state/notices.ts` (a reducer, unit-tested) and drawn by `src/components/NoticeLayer.tsx`, all in polite live regions that never take focus, so a form or the chat box keeps what is being typed:

- broadcasts, sysop messages and (away from the cafe, where the transcript already has them) TV lines are toasts at the top left, newest last, at most four, fading after nine seconds (paused while hovered or focused); a sysop message stays until closed;
- `mail` shows an envelope with the count beside the title ("3 letters are waiting at your desk"); it clears when the player next reaches the desk, where the letters are delivered;
- `newDay` is a banner, "A new day has dawned. It is day N.";
- `sessionEnded` (and a pushed lobby View, which comes first) replaces the game with a clear screen: why (replaced by another log-on, idle, kicked, banned, town reset...), the tournament's winner after a reset, and Back to the front door.

The cafe appends other players' lines to the transcript through pushed Views, so the message box keeps its text and focus; the transcript follows new lines only while the player is at the bottom. A line starting with `/` is just text.

#### Browsers and concurrent runs

Every suite runs once per engine (`online-firefox`, `solo-webkit`...; `FQ_E2E_BROWSERS` picks engines, `e2e:chromium|firefox|webkit` are shortcuts). Install them with `pnpm exec playwright install chromium firefox webkit` (on Ubuntu add `--with-deps`). Locally there are no retries, so a flaky test is visible; CI allows one and lists what needed it.

Two runs may share a machine: each finds free ports for its four servers, builds the bundle into a temporary directory of its own (`vite build` honours `FQ_BUILD_OUT`; the tests use the `bundle` script, which skips the type check), keeps results in `e2e/results/<run>` and gives each server a temporary database. Pin ports with `FQ_E2E_PORT`, `FQ_E2E_STATIC_PORT`, `FQ_E2E_MUSEUM_PORT` and `FQ_E2E_EXPANDED_PORT`.

**WebKit on a distribution Playwright does not support (Arch, Fedora...)** is left out of the default run there (`FQ_E2E_BROWSERS=webkit` or `e2e:webkit` still runs it): with Ubuntu's ICU 74 and libxml2 loaded beside the system's newer ones it can crash (SIGSEGV in `utext_setup`). It needs three libraries its Ubuntu 24.04 build links against: `libicu74`, `libxml2` (2.9) and `libflite1`, plus `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1` (the config sets it on such systems). Without root, `bash tools/linux-webkit-libs.sh` fetches Ubuntu's packages (checksummed), and puts the libraries in the browser bundle's own `sys/lib`. Sound is decoded by the system's GStreamer, so for the music test the host also needs `gst-plugins-good` (its MP4 demuxer; Arch has it as a separate package, not installed here); the test skips itself, saying so, where WebKit cannot decode AAC. Ubuntu's `playwright install --with-deps webkit` installs all of this, which is what CI does.

What the cross-browser and repeated runs found and fixed (so the next flake is not a mystery): the moderation report spec lost a cafe line because the client dropped a line typed while the previous one was still being answered (chat lines now queue, `src/state/useGame.ts`); the injury-panel spec's missing trace came from two runs sharing one results folder (each run has its own now); a gamepad press held for a fixed 70 ms was missed when frames came slowly (presses now last animation frames, not milliseconds); the mouse handing the screen back from the pad relied on `movementX`, which WebKit leaves at 0 (it also compares positions now); zod's `new Function` probe was logged by Firefox as a CSP violation (`src/dev/zodJitless.ts`); a refused `AudioContext.resume()` was an unhandled rejection in WebKit (it is caught: no sound, no error).

## Art packs

Settings, Art style picks the pack; the choice is saved (`artPack` in `fq.settings.v1`). Classic is the default and the fallback for an unknown id; Remastered is the Classic art with new drawings in its style (the twelve traced photographs redrawn, and the Expanded places, people and icons; see `docs/art/remastered-notes.md`); Hand-drawn is the CSS look the shell shipped with.

A pack is a folder, `src/art/packs/<id>/`:

- `pack.json`: `id`, `name`, `description`, and the geometry (below).
- `extends` (optional) in `pack.json`: another pack this one builds on. Every piece, icon, cabinet, fit, map and newspaper it leaves out is the base pack's, and a placeholder it replaces stops being one. Remastered extends Classic, so its chrome is the original's.
- Pictures: a pack may redraw any picture id as `<repo>/assets/<pack id>/<id>.svg` (every folder in `assets/` but `classic`, minus its `ui/` and `icons/`). They are bundled as hashed assets (`import.meta.glob` in `src/art/packs.ts`). A picture layer loads the pack's drawing first, then the asset base's (the Classic art), then the placeholder (`src/components/Picture.tsx`).
- `icons/<name>.svg`: small icons (`ICON_NAMES` in `src/art/types.ts`: the ledger, town strip, `karma-balance`, `parlor-1` to `-5`, `monument-1` to `-5`). `XIcon`, `BuildingGlyph` and `KarmaScale` use them when the pack has them and draw their own glyphs otherwise.
- `ui/<piece>.svg`: the pieces, named by role (`cabinet-main`, `plaque-button`, `deathville-map-base`, `building-bank`, `notepad`, `dialog-panel`, ... see `PIECE_NAMES` in `src/art/types.ts`). Only files that exist are bundled, and `import.meta.glob` finds them, so **a future "Remastered" pack is a new folder with a `pack.json` and some SVGs: no code changes.** It then appears in Settings. A piece a pack leaves out falls back to the drawn chrome for that screen.

Geometry is data. Each cabinet variant (`main`, `generic`, `chat`, `rankings`, `status`) lists, in the piece's own art units, where the picture, note, text well, plaque row, scroll capsule, Exit and settings buttons, luck tube and stats numbers go; `fits` gives design pixels per art unit for the 4:3 and wide layouts; `map` places the nine buildings; `news` places the notices, section bar, story and links. `src/art/geometry.ts` turns that into the CSS variables `src/styles/art.css` reads. Every piece the pack supplies is also a CSS variable (`--art-plaque-button: url(...)`) so stylesheets can use art without knowing the pack.

### Classic: deriving clean pieces

The exported SVGs in `assets/classic/ui/` (generated, never edited) contain Flash placeholder text ("temptext" on buttons, "test" lines, sample numbers, sample names) and shapes the client draws live. `tools/derive-ui-art.mjs` reads the recipes in `tools/ui-art.config.mjs` and writes `src/art/packs/classic/ui/*.svg` (git-ignored, rebuilt by `dev`, `build` and `test`):

- every `<text>` is removed;
- shapes wholly inside a listed rectangle are removed: the five baked plaque buttons, the sample level in the luck tube, the "Class:" and "Mood:" captions, the Exit button, health bars and tag clutter on the note, and (for "caption" recipes, unfilled outline lettering only) English captions that must change with the screen: the notepad's prompt, Cancel and Submit, the notice titles, the stats parchment's labels;
- the drawing is cropped to the cabinet (the exports include off-screen state frames) and `<title>` is dropped;
- map and building pieces get `preserveAspectRatio="none"` because the original stretched the map to the screen.

`tools/svg-clean.mjs` holds the pure functions (path bounding boxes, removal, crop) and is unit-tested, including a check that no derived file contains text.

### What each layout does with the pieces

- **Classic 4:3 (1024 x 745)**: the full cabinet at the original's scale (1.43 design pixels per art unit), the same proportions as the 2001 screenshots. The desk and negotiation sit on `cabinet-main` (stats parchment); a place with a room description on `cabinet-generic`; the cafe on `cabinet-chat`; rankings on `cabinet-rankings` (with the running skeleton); stats on `cabinet-status`. Plaques are the original `plaque-button` drawn live over the cabinet's plaque row, right-aligned as the original did. The lobby, map and newspaper are full-frame scenes.
- **Wide 16:9 (1280 x 720)**: the same cabinet at the same scale, left-aligned, plus a matching walnut side panel (the empty cabinet, `cabinet-frame`, cut into nine slices) holding the log of earlier text. The newspaper keeps its proportions on a repeating brick wall; the map keeps its frame beside a place list.
- **Phone portrait**: no cabinet. The original pieces become stacked cards: `picture-frame` as a nine-slice frame, `parchment-note` as the stats strip and note, `plaque-button` stretched across the full width as 48 px buttons, `logo` as the title, `button-exit`, the casket tag icons, and wood tokens from the cabinet for the page and the text well.

Dialogs (message, confirm, picker, settings, exit) share one olive panel (`dialog-panel`, nine slices) with plaque buttons; text entry is the original spiral notepad.

## Accessibility

Landmarks and order: title (`h1`), your status, notes, picture, text, status line, choices. Dialogs are modal with a focus trap and restore focus. Disabled buttons stay focusable and explain themselves through `aria-describedby`. Luck, resistance and health are native `<meter>` elements. The typewriter animates an `aria-hidden` copy while a screen-reader copy holds the whole text, and it is off by default under `prefers-reduced-motion`. Keys 1 to 9 press buttons (ignored while typing or when a dialog is open). Focus rings are a yellow outline with a black halo so they read on every surface.

Colour text tokens were lightened from the 2001 values where the original failed on the brown text well (the original magenta `#CC66CC` is kept as `--fq-text-number` but numbers use a lighter `--fq-c-purple`). Contrast is measured, not guessed: see "Accessibility checks" below.

## Sound

There are two sound packs, chosen under Settings, Sound pack (saved as `soundPack` in `fq.settings.v1`; the note under the choice says which one is playing). **Synth** (`synth`, the default) is everything below: generated by this repository's own code. **Studio** (`studio`, `assets/audio-studio/`) is music, ambience and effects generated with ElevenLabs from text prompts written for this game (`assets/audio-studio/LICENSES.md`: its redistribution terms are the owner's to confirm, so it is not the default); any sound it lacks plays from Synth. `vite dev` serves both; `vite build` bundles Studio only with `FQ_AUDIO_PACKS=synth,studio` (or `VITE_AUDIO_STUDIO_BASE` hosts it), and a build without it plays Synth when Studio is picked.

The Synth pack: everything heard is generated by code in `packages/audio` (`@fq/audio`): a small synthesiser (organ pipes, plucked strings, mallets, bells, a theremin, brass, drums and noise), a sequencer, the score as note data, the effects and ambience generators, and the cue map from Views to sounds. `pnpm --filter @fq/audio run render` writes `assets/audio/` (Ogg Opus and AAC files, `manifest.json`, `LICENSES.md`); `vite dev` serves it from there and `vite build` copies it to `dist-build/audio` (`FQ_BUNDLE_AUDIO=0` leaves it out, `VITE_AUDIO_BASE` hosts it elsewhere). The UI's clicks, page turns and blips are not files: they are synthesised on the page at start-up.

- **What plays.** `Game` hands every View to `audio.cue(music, sounds, view)` and every action to `audio.action(action)`. The cue map (`@fq/audio` `src/cues.ts`) picks, in order: a fight, a customer (the negotiation, whose three stems follow `customer.moodLevel`), the engine's own `music` id (the Classic fight and sneak), the paper's meteor flag, the scene (map, cafe, desk, news, lobby), the Expanded place by button prefix (`reaper-club:`, `graveyard:`, `city-hall:`...), the picture (`places/bank`, `places/psych`...), the last place visited; and an ambience bed from the picture or the town's weather. One-shots come from the View's `sounds`, from pictures that just appeared (the original's picture sounds: the money bag, the toilet, the gong...), and from what changed (a sale, a walkout, a hit in a fight, a tag earned, a new day, new weather, a letter). The front door plays the main theme.
- **Rules.** Nothing sounds before the first click or key (browsers' autoplay policy); the front door has a "Sound on" button. Music crossfades between scenes (1.2 s, 0.35 s into a fight), ambience over 2 s, the negotiation's stems over 1.5 s; stingers duck the music. One-shots are capped (10 voices, 2 of one sound). Master, music, ambience and effects volumes, mute, the "2001 radio" filter (mono, 150 Hz to 5 kHz, a little grit) and the sound pack are in Settings and persist. A hidden tab suspends the audio. A missing manifest or file is a console warning and silence, never an error. Under Vitest there is no backend at all.
- **Probe.** `window.__fqAudio.debug()` reports the context state, the music and ambience playing, the stem gains and the output level (an analyser), for tests and the curious.

## The native wrappers

The desktop (Tauri) and mobile (Capacitor) apps carry this bundle with `apps/desktop/shim/fq-wrapper.js`, which defines `window.fqWrapper` (and `window.__fqHost`). `src/wrapper.ts` is the client's whole knowledge of it; in a browser neither exists and nothing changes.

- **Server address.** `src/net/config.ts` reads `window.fqWrapper.server` when the page starts (empty means the page's own origin, or the build's `VITE_SERVER_URL`), so the wrapper no longer needs to rewrite requests. Settings has an "Online play" entry, "Server address...", that calls `window.fqWrapper.openSettings()` (only with a wrapper).
- **Saves.** Solo's Export hands the file to `fqWrapper.saveFile(name, text, type)` (the shim keeps the same function on `__fqHost`; either is used) instead of a blob link, and reports success or the failure; Import uses `fqWrapper.openFile(accept)` when the wrapper has it (resolving `{ name, text }` or null), else the page's own file input, which works in both webviews.
- **Back.** `window.fqHandleBack()` is defined while a game or the front door is on screen (`src/util/back.ts`): it closes the top dialog, else leaves the screen through the View's own Back or Leave button (the last enabled button whose id is `go:<place>` or ends `:main` or `:back`), and returns true; it answers false on the desk and in a sale, so the app can ask "Leave Funeral Quest?".
- **No service worker** is registered inside a wrapper.
- **Gamepad.** The page owns it (below) and sets `window.fqClientGamepad = true`.

## Gamepad

`src/input/gamepad.ts` (pure functions and a controller, driven by a synthetic pad in the tests) and `PadProvider`, for the standard mapping: the d-pad and left stick move the focus to the nearest control in that direction (plaques, cards, the map's places, form fields, tabs, inside the top dialog when there is one; auto-repeat while held); A presses the focused control (a text field is focused instead: the on-screen keyboard is the platform's job); B goes back (`fqHandleBack`: dialog, else the screen's own Back or Leave); X submits the form the focus is in (a prompt, the cafe's box, a sign-up), so a text prompt needs no trip to its Submit button; LB, RB and the right stick scroll the text; Start opens or closes Settings. A glyph bar shows what the buttons do (the pad's own labels: A B X, the PlayStation symbols, a Nintendo pad's swapped A and B, "Menu" or "Options" for Start) while a pad was the last thing used, and goes away with the first mouse move, key or touch (`<html data-input="pad">`, which also draws the focus ring for a script-moved focus).

## Accessibility checks

`e2e/a11y.spec.ts` runs axe-core (WCAG 2.0 and 2.1, A and AA) on the front door, Solo's list, the desk, a sale, the map, the office, the catalogue, the bank, Bingo, City Hall, the club's tables, the monuments, the stats sheet and Settings, in both art packs at 1024x745, 1280x720 and 390x844, and fails on any serious or critical finding. axe cannot judge text over art ("needs review" for nearly all of it), so `e2e/contrast.ts` measures it as drawn: every visible piece of text, its colour and size, against the page repainted with the text made transparent (the worst tenth of the sampled points ignored), 4.5 for text and 3 for large text; inactive controls are exempt. What it found and `src/styles/contrast.css` fixes: parchment text tones too light for the darkest paper (the light tokens are darker, the panels' paper lighter), the yellow text on the lightest part of the well (a faint shade), cream labels on the town strip, plaque lettering (a light wash over the art), the front door's choice buttons, the ladder's dimmed names, and scrolling regions that had no keyboard stop (`useScrollable`: a region that scrolls gets `tabindex="0"`, a role and a name).

## Known gaps

- The map only sends `{ id, label }` per place. The ids are fixed by the game: `funeral-home`, `bank`, `store`, `cafe`, `yangs`, `competitors`, `church`, `hospital`, `spirit-university`, and in Expanded towns `graveyard`, `city-hall`, `reaper-club`. Building positions come from the pack (`map` in `pack.json`; the hand-drawn map uses `src/scenes/mapData.ts`). An unknown id gets a visible labelled pin along the bottom edge, and the place list outside the 4:3 layout.
- Classic: the cafe's chat room is its own cabinet, so the cafe's picture and note are not shown there; the settings button has no original art (it is a copper disc like Exit); the original's page-curl and tab buttons (`newspaper-tab-*`, `button-scroll-*`) are not used because their jobs are done by the live buttons.
- Expanded, still read from the View's words or hints because it does not say it structurally (the graveyard's monuments now come from `View.monuments`: the stones that stand are lit): the disabled cards that are not upgrades, ballots or choosers (a permit already held, a place not yet unlocked) are sorted locked, short or yours from their hint; the Reaper Club's rules line and the contractor's description sit in the text as before.
- Sound: where the engine says what happened, the cue map uses it and reads no text: the season's meteor theme from `news.meteor`, a sale's outcome (exact, great, walkout) from `View.saleOutcome`, a letter, notice or reward sound from the message overlay's `messageKind`. A Classic View carries none of these (its transcripts are locked), so for Classic the original's own words stand in (an exact-match fanfare by "PERFECT!", a walkout by a customer leaving at mood 8 or more, a letter by the words "letter" or "mail"); all in `packages/audio/src/cues.ts`. Everything else the fields say (a round's outcome, an upgrade bought, a loan taken or repaid, a card bought, an injury, a karma band crossed) is a cue from data (`src/audio/dataCues.ts`). Reporting an Expanded cafe line names the speaker by `ChatLine.from` (the player id), not by parsing the line.
- Installing needs HTTPS or localhost. The page, service worker and manifest use absolute paths, so the site must be served from a host's root, not a sub-directory.
- Unsaved typing in the cafe box or a notepad is not kept across a reload; the session itself is.
